Part I

Orientation

Why I built this, how to read the page, and the shape of my setup.

Why I engineered a harness

Claude Code is the agent; the harness is everything I have configured around it: instructions, guardrails, capabilities, verification machinery, and memory. I built it because the failures I design against are process failures: a fabricated citation, a join that silently drops records, a tool reaching data it should never touch. A better model does not remove these risks; process does, the way human error in a study is managed by protocol rather than by hiring cleverer humans. Four goals govern every choice, in order: correctness, data safety, auditability, efficiency. The rule throughout: put friction where mistakes are irreversible, and grant autonomy where they are cheap.

In more depth

The build itself is treated like a study: rules earn their place through measured effect and are retired when they stop paying rent. Every count on this page is a live probe of the configuration taken on the date above (a few individual items are not listed, and the counts reflect that); the few numbers that cannot be re-measured at build time carry their measurement date instead. Nothing is quoted from memory, including the agent’s own.

How to read this page

I assume you already know the basic Claude Code concepts (agents, hooks, permission rules, skills, subagents, memory, MCP), so the page skips the introductions and goes straight to what my setup does and, where it seems worth saying, why. Where a concept needs more background than a sentence, I would rather point at better teachers than paraphrase them: the official documentation at code.claude.com/docs covers every mechanism named here (instructions, hooks, permissions, skills, subagents, memory) under the same names, and Anthropic’s engineering articles explain agent design far better than I could. Two reading aids: each module opens with a short summary whose bold phrases carry the load, and the “In more depth” folds hold the personal detail of how I actually run things; on wider screens, the button in the navigation bar expands them all at once.

My system at a glance

One diagram, six layers: this is my whole setup on a page. A task enters on the right and flows down: it is aligned (restated as checkable success criteria), executed using the capability layer under the watch of the enforcement layer, verified in proportion to its stakes, and reported with evidence. What the session taught flows into memory, and scheduled audits watch the whole machine.

Pause exceptions ride across the whole flow rather than sitting in it: an enumerated list of situations (irreversible actions, scope changes, missing information) where the agent must stop and ask rather than proceed, whichever phase it is in.

In more depth

A worked example: “summarise these twenty papers into a table” arrives. Alignment restates it (which papers, which columns, what counts as done) and confirms nothing is missing. Execution fans the reading out to subagents, drafts the table, and cites each source. Enforcement silently checks every file it touches. Verification re-checks each citation against the bibliographic record because that error class survives self-review. The report separates what was verified from what was not, and the one lesson learnt about a mis-formatted source becomes a memory note.

The diagram doubles as a map of this document: layers one to six correspond to the modules that follow, and the catalogue in Part VI works through the instruction, enforcement and capability layers item by item.

Part II

The core contract

How a task moves from request to verified result.

The task lifecycle contract

Every task runs under a five-part contract: Align, Execute, Pause exceptions, Verify, Report. At intake the task is restated as checkable success criteria; if success cannot be verified, ambiguity would change the approach, or information is missing that only I hold, the agent asks first; otherwise it runs to completion. Within a task I have defined, autonomy is the default, revoked only at a closed pause list: irreversible or outward-facing actions, genuine scope changes, information only I can supply, edits to safety-critical configuration (consent must name the specific file), and security gates no blanket “just do it” can loosen. When in doubt whether a pause applies, it does.

In more depth

One permanent reservation makes the philosophy concrete: the agent stages and commits code but never pushes to a remote. When a push is the right next step, it prints the exact command and hands over. Publication, in any form, stays a human act.

Reporting discipline closes the loop: the first sentence states what happened; failing output is pasted verbatim, never paraphrased; every claim is separated into verified via tool output versus unverified. Fabricated progress is treated as the worst possible failure, worse than honest failure, because it poisons trust in every future report.

Some error classes are blindness-type failures, invisible to self-review: a fabricated citation is internally consistent, so citations, transcribed numbers and cross-references are checked with tools against the external record. From L3 up, isolation is the active ingredient: the reviewer never inherits the authoring conversation. And verification always runs on the strongest model. Isolated review reopened work self-review had passed in 71% of L4 and 77% of L3 runs (a run counts when any isolated reviewer, a panel member or the final gate, reopened it; 254-run recount, November 2026; internal, not independently audited), so the gate stays.

In more depth

How a level is chosen: score the stakes and the irreversibility, take the higher, and when in doubt round up. The looped forms continue review rounds until a full pass lands clean. At L2 the loop runs inline: review and fix until one full-coverage round finds nothing critical or major, then one last round re-read from disk that changes nothing, which catches the defect a fix itself introduced. It buys no independence, though; the same context is re-reading itself, and that is what L3 adds. At L4 the loop adds isolated reviewers and a final gate on the strongest model, because the files it guards are the ones every future session inherits. A loop that runs out of rounds records its exit as paused, never as passed.

For changes to the harness itself, the isolated panel also takes a reviewer from another model family, a GPT model, and a DeepSeek model can join as a second outside family, because a Claude reviewer shares Claude’s blind spots. They add coverage, not authority: the final gate still runs on the strongest Claude model. The DeepSeek route also sits behind an explicit egress gate of its own, and credentials never pass it.

An isolated review is mechanically separated from the author: a fresh agent, a clean context, the work read back from disk rather than from the conversation, and a verdict returned in a structured file that records which model actually performed the review, so the check leaves an audit trail of its own.

The evidence line is the cheapest habit in the whole system: one line in every routine completion report separating claims verified against tool output from claims merely believed. It makes overclaiming structurally awkward.

Part III

Safety architecture

Why the agent is treated as untrusted, and what enforces that.

Research-data isolation

The agent is designed never to access drives other than C, and it is treated as untrusted software with respect to them: independent enforcement layers block its tools from those drives entirely, and the rule supersedes every convenience. Enforcement is code rather than instructions because an agent that can read a file can be tricked into echoing it (prompt injection is real); a boundary worth having must hold even when the agent is wrong, confused, or manipulated. Three layers: static permission rules denying whole path classes; runtime hooks inspecting the covered tool channels before a call executes; and written policy for the residue no pattern-matching can catch. Residual risks are catalogued, and the layers are re-exercised weekly rather than assumed sound. Two honest limits: this is defence in depth at the tool layer, not an operating-system security boundary (the outermost lines remain the organisation’s approvals and access controls), and the friction is accepted, because data breaches are irreversible and inconvenience is not.

Deterministic guardrails

Model compliance is probabilistic; guardrails are not. Hooks, small programs firing on events like before every tool call, enforce rules in code whatever the model believes; 22 are registered, alongside a 120-entry deny list, and the catalogue below names each. Guards that protect data fail closed; advisory paths fail open but warn; where fail-closed would be worse than the risk, the exception is documented, not hidden. Two habits keep it honest: guards must prove they can fail, audit scripts injecting faults to prove each check still fires (a check that cannot fail is decoration); and honesty about limits, literal pattern-matching documented as a speed bump, not a security boundary. False positives are accepted: a blocked convenience beats a silent breach.

In more depth

The layers are deliberately redundant. Static deny rules and runtime hooks block independently, so either can catch what the other misses, and the written policy covers what no literal matcher can see, such as a path assembled at run time. Defence in depth is the admission that every single layer has holes. Time is one of those holes: a hook that runs out of time lets the call through, so a tool call too large to be checked within the limit is refused outright, and the shell guard refuses every command if the drive check it relies on is missing or fails to load, rather than running without it.

The self-testing is specific rather than rhetorical. The two most dangerous guards ship with their own weekly test suites: every pattern is exercised individually, seeded faults must be caught, and the suite pins its expected case count so a silently shrinking run reads as failure. Even the guards’ documented over-blocks, benign commands they wrongly refuse, are pinned in the tests, so a later “fix” that quietly widens a hole fails the suite instead of shipping.

Part IV

The capability system

The layers that make the agent capable without making it reckless.

Layered instructions and rules

The instruction layer is one global file plus 15 rules files, one domain each; four load only when the work touches matching paths, and the other eleven are always resident. The context window is a budget, so the resident set is held at roughly 102,000 characters, 42% below its undieted baseline (measured 24 November 2026, in characters). Two disciplines keep the layer maintainable: single definition point, each rule stated once and pointed at everywhere else, because copies drift and pointers do not; and selective loading, so the R style guide spends nothing in a session about slide design.

In more depth

The instruction layer is treated like reference software, not notes: rules carry dates, cross-references, and known-limitation sections, and a weekly audit checks that every cross-file reference still holds. When two files disagree, one of them is declared canonical and the other becomes a pointer. Ties are never left standing. The four path-scoped files are the coding style, a reference script skeleton, the proofreading protocol and the quality rubrics; the fifteen listed here are named in the catalogue.

The budget holds because of progressive disclosure: a resident rule keeps only its operative text, and the history, forensics and worked reasoning behind it move word for word into reference files the agent opens only when the rule points there. Replies have a budget too: an optional compressed output style, adapted from an open-source prompt, trims filler at three strengths but never touches numbers, negations, the evidence line or the markers that say how firmly a claim is held, and anything written to a file stays in plain prose. The resident files also carry size ceilings, one for the whole set and one per file, measured weekly and flagged at edit time, and the quarterly review described under self-auditing puts every resident line to one test: does any run actually read it?

Skills and the learning loop

A skill is a packaged procedure the agent loads on demand, an SOP. The library holds 193 of them, 211 skills/commands once the commands are counted in: domain and workflow skills and, the class I value most, hard-won debugging lessons written up so no problem has to be solved twice; agents have no episodic memory, so an uncaptured pitfall is rediscovered at full price. The library is curated like an SOP register, with re-evaluation dates and one hard rule: every third-party skill passes a security vetting protocol before first use, because a skill is instructions written by a stranger. The cost of it: an untended library rots into contradictory advice.

In more depth

Anatomy of a skill: a folder, one SKILL.md whose header carries a name and a one-line trigger description, and optionally scripts and reference files. The trigger line is where the engineering lives. It decides when the skill surfaces, and a vague one means the lesson sleeps through the exact situation it was written for.

Those trigger lines are themselves a budget, because the listing of every skill rides along in every session. So the listing is tiered: 26 skills keep their full description, 105 are listed by name alone and still load on demand, and 62 with no recorded use are switched off. A description that outgrows the listing’s cut-off would lose its trigger words without any error, so a check flags it at commit time as well as in the weekly audit.

Vetting, for anything third-party: read the full text before first use, check what it asks the agent to run and where it would send data, record the verdict in a registry, re-vet when the upstream changes. The registry reconciles against the on-disk library in both directions, and that reconciliation is itself audited.

After every task: retrospection and self-evolution

If I had to pick one part of the setup as its most distinctive, it would be this. At the completion of any substantive task, the agent runs a standing retrospection check: did this work produce something whose value outlives it, either a correction that generalises or a method verified here that would otherwise be re-derived from scratch next time? A hit is not archived on first sight. It becomes a tentative note at low starting confidence, and repeated observations from different sessions or dates raise that confidence; only a note that clears a promotion bar (confidence at or above 0.9, observed in at least two distinct sessions or dates) earns a proposal to become a full skill or lesson, which I approve or skip. One sighting never archives anything: recurrence, not how striking the moment felt, is what promotes. Every self-evolution proposal also passes a necessity review first (is the status quo actually broken, or does proposing feel like progress?), and anything promoted into a skill still passes the same vetting gate as everything else.

In more depth

Two further pieces close the loop. The heavyweight review skill keeps its own pitfalls ledger: when a check is fooled once, the episode is written into the skill’s pitfalls file with its tell-tale signs, so the next review round starts warier than the last. And skill files themselves are periodically evaluated against a structured quality rubric by a dedicated improvement skill, which proposes concrete edits rather than silently applying them. Proposals do not nag either: one I skip comes back after a fortnight at the earliest, and two refusals in separate sessions end the automatic offers for good, although I can still promote the note by name.

What the mechanism has produced so far: the largest single class in the memory store is captured lessons, and a large share of the skill library is narrow lesson capsules that fire rarely by design. A capsule that triggers once a quarter and saves an afternoon each time has felt like a good trade.

Subagents and model routing

A subagent is a separate agent instance with its own clean context. Six custom agents are defined, review roles pinned to the strongest model, mechanical roles on lighter ones; the catalogue below describes each. Two reasons to spawn one: isolation, an independent reviewer must not share the author’s context or it inherits the author’s blind spots; and offload, bulk reading in a disposable context that keeps the main session’s working memory clear. Routing follows one rule, the cheapest model that clears the quality bar, with one exemption that never moves: no cost-saving mode may downgrade a reviewer. Spawning costs; a necessity gate precedes fan-out.

In more depth

The pinning matters as much as the choice: each agent’s model and effort are fixed in its own definition file, so a busy session cannot quietly hand a verification job to a cheaper reviewer. A review role on a lighter model is the routing rule working as intended: the bar is set by the task, not the job title. Dispatches of mechanical work name their lighter model explicitly rather than inheriting the session’s, so the saving is a decision, never an accident, and each launch is logged with the model that actually ran, which is how routing drift would be noticed.

The memory system

Persistent memory is a folder of typed Markdown files, 185 in the live store: preferences, feedback (“corrected once; never again”), project state, references, behind an index loaded at session start. The repository records what the code does; the memory records what only conversations know. The store is budget-guarded: the index is re-measured by a hook after every edit, and every note except the archives has a size ceiling checked weekly, so nothing in use can silently bloat; wrong memories are deleted, because a wrong memory is worse than an assistant with amnesia.

In more depth

The store’s shape says what experience taught: the largest single class is captured lessons (72), ahead of reference pointers (37) and feedback corrections (34), with 17 project-state notes. The largest class is exactly the one that stops repeated mistakes; the catalogue breaks the store down. Notes stay lean by moving rather than deleting: version history, superseded readings and old case narratives go word for word into an archive folder, and the change log rotates into monthly archives, so the live files hold only what is current.

Form matters more than volume. A feedback note records the why and the how-to-apply, not only the correction, because a rule without its reason gets misapplied. Corrections to old notes quote the superseded wording instead of overwriting it, the discipline a lab notebook demands. And because several sessions can run at once, shared files are re-read immediately before writing and checked immediately after, which shrinks the window in which two sessions could trample each other.

Commands and integrations

Custom slash commands encode recurring rituals as executable checklists, from intake charters to decision briefs and handovers. 27 are defined, several as escalation chains, a light default deepened by flags as stakes rise; anything done twice by hand ends up inconsistent. Integrations follow a minimal-surface policy: 4 tool servers, all configured directly, each security-assessed before connection, read-only preferred, unused ones removed; every integration is also attack surface.

In more depth

The decision brief is the ritual I lean on most: whenever a non-trivial choice needs me, the agent leads with a compact, self-contained brief (background, verification tier, the core trade-off, options, a recommendation) so the decision can be made in seconds without re-reading the analysis. Delegation works when deciding stays cheap. A companion command gathers everything still waiting on me into one numbered list, blocking items first, each with where to go and what to run.

Escalation chains keep one name for one job at every depth: the review command runs light by default, and flags add drain rounds, an isolated reviewer, or a second model family as stakes rise. The alternative, a different tool at every tier, is how rituals die. The most-used commands are listed with the skills in the skill library.

Several sessions often run side by side, so they can coordinate directly: a session can list the other agent sessions on the machine and message one, and a terminal multiplexer reaches an agent from another vendor that maintains its own port of this harness. A message from another agent is treated as information to weigh, never as my instruction, and it can never grant a permission I have not given.

Part V

Keeping it honest

The machinery that audits the machinery.

The self-auditing harness

The harness audits itself on a schedule: a weekly configuration-drift audit, a weekly security review, a watchdog on the audits themselves, and daily backups; configuration rots silently, and the alternative is discovering rot from its consequences. Its checks are themselves checked: fault-injection deliberately breaks the guards that matter most and requires the audit to notice, so a green result cannot come from a check that quietly died. Beyond the schedule, a stumble-detection rule: any defect that reaches me escalates that task class one verification level, for good.

In more depth

Two habits from this module have served me beyond it. Log every variance: when reality and the record disagree, the discrepancy is written down before it is resolved. And measure the monitor: an audit that has never flagged anything is assumed broken until fault injection proves otherwise.

Once a quarter a deeper review, which only I can start, goes over the whole harness. Its first stage only reads: each dimension of the harness gets its own isolated reviewer, and no reviewer’s conclusion counts until the main session has checked it. Slimming is one of its standing questions. In the second stage nothing changes without my approval of that exact item, and the review passes only if its instruments show no new failure, the resident instructions have not grown without a line-by-line account, and every change that landed was approved and verified.

The records the audits rely on are guarded at the point of writing. Each review round leaves a structured log line, and those lines, like the record of which reviewer said what, are appended only through a validating writer that rejects a malformed row instead of storing it, so the evidence behind figures such as the reopen rates cannot quietly decay. Clean-up follows the same caution: deletion needs a recovery window, so cleared files move to a holding area whose expiry window is declared before anything enters it, and the few places that still delete their own scratch files outright are listed as open items rather than ignored.

Design principles and trade-offs

Eight principles I keep coming back to.

  1. Bounded autonomy Free by default, stopped at enumerated gates; never the reverse.
  2. Determinism over trust What must not depend on the model’s judgement is enforced in code.
  3. Verification scaled to stakes And the gate never moves, whatever the economy drive.
  4. Evidence-based tuning The harness is measured like a study; rules that stop earning their keep are retired.
  5. Friction as a feature Where errors are irreversible, the human pause is the control.
  6. Quality is never traded for tokens Efficiency only where the outcome is provably unchanged.
  7. One definition point Canon stated once, pointed at everywhere else.
  8. Honest limits Every guard’s blind spots are documented and owned, not wished away.

The frame that made all of this feel manageable to me: treat the harness as a study protocol for working with an AI. Pre-registered decisions, access control, QC proportional to stakes, an audit trail. The instrument was new to me; the epistemology was not, and borrowing it saved me from designing on instinct.

TensionHow it is resolved

Part VI

The catalogue, item by item

Everything above described the design; this part names the components behind most of these numbers, with what each one does, in case any of them fits your work. Identifiers tied to people, projects, or data providers are held back, as is the exact text of the guard patterns.

The skill library

The library holds skills and commands as one set, so its unit here is the skill/command. A skill is a folder holding one Markdown procedure plus any scripts it needs, with a one-line description that tells the agent when to load it; a command is a single file that the user or the agent calls by name after a slash. Where a command only forwards to a skill of the same name, the two count as one entry, listed under the skill’s name: 211 skills/commands in all (193 skills and 27 commands, nine of them such wrappers). The library grew one lesson at a time; nobody sat down to write 211 procedures. The 120 deny rules

Deny rules are static permission entries evaluated before anything runs, a separate layer from the hooks so that either can catch what the other misses. They fall into six families. Exact patterns are deliberately not reproduced here; the families and their logic are the transferable part.

FamilyEntriesWhat it stops
Research-drive isolation75Reading, editing and searching are each denied across every non-local drive letter: three tools times twenty-five letters, enumerated in full rather than pattern-matched, so there is no wildcard logic to slip past. Typical catch: a file read whose path names any other drive letter is refused before it runs. What enumeration cannot see is named below.
Destructive version-control commands10Force pushes, hard resets and tree-wide restores. Git itself stays available; its irreversible spellings do not. Typical catches: git push --force, git reset --hard.
Recursive deletion of protected roots10Delete commands aimed at the home directory, the user tree or the filesystem root. Typical catch: rm -rf pointed at the home directory or the configuration folder.
Credential and secret reads9Private keys, environment files, cloud credentials and browser credential stores. Typical catches: reading an SSH private key or a .env file.
Credential and secret writes6Key material stays unwritable as well as unreadable. Typical catch: a write landing in a key store or an environment file.
Literature-service write tools10The write actions offered by one connected literature service.

Two habits behind the list. Deny entries match literal spellings, so the internal policy honestly records what they do not catch (a path assembled at run time, for instance) and assigns that residue to the hooks and to written policy instead of pretending the list is airtight. And the list is audited: entries that a validator proves inert get removed, with the reasoning logged.

The six custom agents

Each agent file pins a role, a model tier and an effort level, so a busy session cannot quietly hand review work to a cheaper reviewer. Reviewers sit on the strongest tier; bounded retrieval and mechanical work sit on a lighter one.

AgentTierRole
domain-reviewerstrongestSubstantive review of quantitative reasoning: causal assumptions, methods validity, reporting compliance, citation fidelity.
r-reviewerstrongestR code review: correctness, reproducibility, figure generation, style compliance.
verifierstrongestEnd-to-end output verification: does it compile, render, and hold together as a deliverable.
literature-reviewerlighterStructured literature search across bibliographic sources.
paper-minerlighterExtraction of structure and data from supplied papers.
proofreaderlighterGrammar, typos, overflow and consistency in formal documents.

A review role on a lighter model is not a contradiction. Proofreading is bounded, mechanical and cheap to re-run; pinning it to the strongest model would buy nothing.
